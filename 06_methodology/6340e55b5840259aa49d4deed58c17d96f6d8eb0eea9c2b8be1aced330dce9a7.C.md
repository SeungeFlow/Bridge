# AI.Style — 언어친화적 구조화 프로그래밍

## 0. 문서 목적

이 문서는 인공지능과 함께 수행하는 현대 프로그래밍에서
자연언어 문서를 단순 설명문이 아니라
목적·경계·상태·관계·변환·검산·복구를 담은
상위 프로그램 소스로 사용하는 방법을 정의한다.

AI.Style은 코드를 폐기하는 선언이 아니다.

```text
AI.Style
=
자연언어로 작성된 구조계약을
AI가 해석·분해·계획·구현·검산할 수 있게 하는
언어친화적 프로그래밍 Method
```

코드는 필요할 때 생성되는 실행형 중 하나다.

```text
구조문서
→ 실행계획
→ 코드 / 설정 / 문서 / 데이터 / Git 변경 / 도구행동
```

# 1. 기본 입장

## 1.1 현대 프로그래밍의 출발점 변화

전통적인 프로그래밍은 사람이 기계 실행문을 직접 작성하는 비중이 높았다.

```text
사람의 목적
→ 사람이 알고리즘과 코드를 직접 작성
→ 기계 실행
```

AI.Style에서는 사람이 먼저 목적과 구조를 언어로 외부화한다.

```text
사람의 목적·가치·경계
→ 언어친화적 구조문서
→ AI의 구조해석
→ 구현후보 생성
→ 검산
→ 실행형 결정화
```

따라서 프로그래밍의 최초 작업은
문법적으로 맞는 코드 한 줄을 만드는 것이 아니라
무엇을 왜 만들고,
무엇을 바꾸며,
무엇을 보존하고,
어떤 상태에서 완료 또는 HOLD할지를
명확하게 구조화하는 것이다.

## 1.2 정확한 판정

```text
“현대 프로그래밍은 코드가 아니라 글이다.”
```

라는 문장은 방향은 맞지만 절대문장으로는 부족하다.

정확한 정의는 다음이다.

```text
AI-native Programming
=
언어로 구조를 먼저 프로그래밍하고,
필요한 실행형을 코드 또는 다른 Artifact로 파생시키는 것
```

```text
언어구조
≠ 실행코드의 완전한 대체

언어구조
=
실행코드보다 상위에 놓일 수 있는
목적·정책·관계·검산 Source
```

# 2. 구조공리

## 2.1 완전한 존재 공리

```text
하나의 완전한 존재는 나누지 못한다.

그저 차이와 관계를 읽기 위해
위치·상태·방향·경계를 구분할 뿐이다.
```

AI.Style 문서는 대상을 임의의 항목으로 해체하여
원래 Identity를 잃게 해서는 안 된다.

구조화의 목적은 분할이 아니라 판독이다.

```text
Structure
≠ Destructive Division

Structure
=
Identity-preserving Distinction for Relation
```

## 2.2 관계 Guard

```text
relation is not merge.
relation is interconnecting.

structure is not isolate.
structure is relation processing.
```

문서 안의 Source·Definition·Method·Result·Executor는
Relation될 수 있지만 서로의 Identity를 잃고 병합되지 않는다.

## 2.3 대상 우선 공리

```text
Target is not confined by Method.

Method exists to reveal the Target,
not to force the Target into the Method.
```

AI.Style의 Schema와 Template는 대상을 읽기 위한 Method다.
대상이 Template에 맞지 않으면 대상을 변형하지 말고
Template를 확장하거나 `METHOD_NOT_APPLICABLE`을 선언한다.

# 3. AI.Style의 프로그래밍 단위

AI.Style에서 하나의 프로그램 단위는
코드 파일이 아니라 `Structured Program Object`다.

```text
Structured Program Object
=
AI가 목적을 이해하고
실행계획과 결과를 역추적할 수 있는
언어기반 구조계약
```

최소 구성요소는 다음과 같다.

```yaml
ai_style_program:
  identity:
  purpose:
  target:
  source:
  definitions:
  axioms:
  reference_field:
  state_field:
  current_state:
  desired_state:
  relations:
  constraints:
  allowed_changes:
  forbidden_changes:
  method_candidates:
  process:
  expected_outputs:
  validation:
  hold_conditions:
  recovery:
  execution_route:
  approval_gate:
```

모든 항목을 매번 강제로 채우지는 않는다.
그러나 누락된 항목이 실행의 의미를 바꿀 수 있다면
`OPEN` 또는 `SOURCE_MISSING`으로 외부화한다.

# 4. 구조문서의 세 층

## 4.1 사람 친화층

사람이 읽고 수정하기 쉬운 자연언어 영역이다.

```text
목적은 무엇인가?
왜 필요한가?
무엇을 바꾸는가?
무엇을 절대로 바꾸지 않는가?
어떤 결과를 성공으로 보는가?
```

## 4.2 AI 결속층

AI가 자연언어의 의미를 실행 가능한 관계로 정규화하는 영역이다.

```text
Identity
Purpose
Boundary
State
Relation
Condition
Transformation
Validation
Recovery
```

## 4.3 실행층

구조계약에서 파생된 실제 실행형이다.

```text
Code
Configuration
Database Migration
Git Commit
Document
API Call
Tool Action
Test
Evidence Package
```

세 층은 서로 대응하지만 동일하지 않다.

```text
사람 친화층
≠ AI 내부표현
≠ 실행 Artifact
```

# 5. AI.Style 문장형

## 5.1 Identity 문장

대상이 무엇인지 고정한다.

```text
대상 Repository는 SeungeFlow/Principle_C다.
대상 Branch는 Start_Position이다.
현재 문서의 Identity는 AI.Style Method Candidate다.
```

## 5.2 Purpose 문장

결과가 아니라 존재이유를 고정한다.

```text
목적은 자연언어 구조문서를
AI가 구현·검산 가능한 상위 프로그램 소스로 만드는 것이다.
```

## 5.3 Boundary 문장

허용과 금지를 분리한다.

```text
새 독립 Method Object 생성은 허용한다.
기존 이론객체의 무근거 덮어쓰기는 금지한다.
```

## 5.4 State 문장

현재와 목표상태를 분리한다.

```text
현재 상태는 CANDIDATE다.
목표 상태는 REVIEWED_AND_READY_FOR_INTEGRATION이다.
```

## 5.5 Relation 문장

객체 사이의 연결과 Identity 보존을 명시한다.

```text
AI.Style은 Data–Function–Result Process를 사용한다.
AI.Style은 기존 Process 문서를 복제하거나 병합하지 않는다.
```

## 5.6 Transformation 문장

무엇이 어떤 상태로 변하는지 명시한다.

```text
자연언어 Source를 구조계약으로 정규화한다.
구조계약을 실행계획과 검산조건으로 펼친다.
```

## 5.7 Condition 문장

조건에 따른 경로를 고정한다.

```text
Identity가 불명확하면 실행하지 않고 HOLD한다.
원격 Readback이 검증되면 완료상태로 승격한다.
```

## 5.8 Validation 문장

무엇으로 성공을 확인하는지 고정한다.

```text
결과는 원래 Purpose와 Boundary에 역추적 가능해야 한다.
변경파일은 예상범위를 벗어나지 않아야 한다.
```

## 5.9 Recovery 문장

실패 뒤의 안전경로를 고정한다.

```text
오류가 발생하면 과거를 삭제하지 않는다.
오류상태를 보존하고 Successor Result를 생성한다.
```

# 6. 강도와 의무를 표현하는 언어

AI.Style 문서는 모호한 권고와 강제규칙을 분리해야 한다.

| 한국어 | 구조 의미 |
|---|---|
| 반드시 | MUST |
| 금지한다 | MUST NOT |
| 허용한다 | MAY |
| 권장한다 | SHOULD |
| 가능하다 | CAN |
| 조건부로 | IF / WHEN |
| 전까지 | UNTIL |
| 실패하면 | ON FAILURE |
| 검증 후 | AFTER VALIDATION |
| 미확정 | OPEN |
| 실행중지 | HOLD |

예:

```text
원본은 반드시 보존한다.
Force Push는 금지한다.
새 독립 객체 생성은 허용한다.
Canonical 위치는 검산 후 확정한다.
Identity가 불명확하면 HOLD한다.
```

# 7. AI.Style Compilation Flow

AI.Style에서 Compilation은
자연언어를 곧바로 코드로 번역하는 단일 단계가 아니다.

```text
Source Language
→ Structural Parse
→ Identity Binding
→ Definition Binding
→ Ambiguity Detection
→ Conflict Detection
→ Method Candidate Selection
→ Execution Plan
→ Artifact Generation
→ Validation
→ Evidence Binding
→ State Rebind
```

## 7.1 Structural Parse

자연언어에서 다음 후보를 추출한다.

```text
존재
상태
사건
위치
시간
방향
경계
조건
차이
관계
목적
금지
완료조건
```

## 7.2 Binding

추출된 표현을 실제 대상과 결속한다.

```text
“Repository”
→ 어느 Repository인가?

“수정”
→ 어느 Branch·Path·Object인가?

“완료”
→ 어떤 Evidence가 있어야 완료인가?
```

## 7.3 Ambiguity와 Conflict

AI는 모호성을 임의로 숨기지 않는다.

```yaml
interpretation_state:
  ambiguity:
  conflict:
  missing_source:
  assumptions:
  confidence:
```

실행을 바꿀 수 있는 모호성은 다음 상태로 외부화한다.

```text
OPEN
SOURCE_MISSING
CONFLICT_UNRESOLVED
HOLD_WITH_IDENTITY_FAILURE
HOLD_WITH_BOUNDARY_CONFLICT
```

## 7.4 Method Selection

하나의 고정 Method를 모든 대상에 강제하지 않는다.

```text
Data Profile
→ Method Candidate Pool
→ Active Lineup
→ Independent Results
→ Relation Validation
```

## 7.5 Execution

실행은 별도 Gate 뒤에서 일어난다.

```text
구조계약 승인
→ 실행지시 생성
→ 실행자 Binding
→ Mutation
→ Readback
→ Closure
```

# 8. Data–Function–Result 재귀

AI.Style 문서 자체도 Process 안에서 역할이 바뀐다.

```text
승이의 자연언어 Source
→ Data₀

gpt.think의 구조화
→ Function₀

AI.Style Method 문서
→ Result₀
```

검산된 Result는 다음 단계의 Data가 된다.

```text
Result₀
→ Data₁

Repository Integration 설계
→ Function₁

GitHub 반영지시
→ Result₁
```

구현과 검산 뒤에는:

```text
Result₁
→ Data₂

실행결과 Readback
→ Function₂

Verified Closure
→ Result₂
```

역할이 변해도 객체 Identity와 계보는 보존한다.

```text

```

# 12. AI.Style 최소 Template

아래 Template는 사람 친화적으로 작성하되
AI가 구조적으로 읽을 수 있는 최소형이다.

```markdown
# <Program Name>

## 1. Identity
무엇을 대상으로 하는가?

## 2. Purpose
왜 이 작업을 하는가?

## 3. Source
어떤 원천과 결정계보에서 출발하는가?

## 4. Definitions
이 문서에서 사용하는 핵심단어의 뜻은 무엇인가?

## 5. Current State
현재 무엇이 형성되어 있고 무엇이 비어 있는가?

## 6. Desired State
작업 후 어떤 상태가 되어야 하는가?

## 7. Relations
대상들은 어떻게 이어지며 무엇을 병합하지 않는가?

## 8. Allowed Changes
무엇을 새로 만들거나 바꿀 수 있는가?

## 9. Forbidden Changes
무엇을 절대로 바꾸지 않는가?

## 10. Process
어떤 순서로 Data를 읽고 Function을 적용하는가?

## 11. Outputs
어떤 문서·코드·데이터·Evidence를 만들어야 하는가?

## 12. Validation
어떤 증거로 성공을 확인하는가?

## 13. HOLD Conditions
어떤 상태에서 실행을 멈추는가?

## 14. Recovery
실패하면 어디서 어떻게 이어 가는가?

## 15. Execution Route
누가 설계하고 누가 실행하며 누가 승인하는가?

## 16. Final State
완료상태의 정확한 이름은 무엇인가?
```

# 14. 완료판정

AI.Style Program은 문서가 길다고 완료되지 않는다.

다음 조건이 충족되어야 한다.

```text
Purpose가 분명하다.
Target Identity가 고정되었다.
현재와 목표상태가 분리되었다.
허용변경과 금지변경이 분리되었다.
실행자와 승인자가 구분되었다.
모호성과 충돌이 숨겨지지 않았다.
결과를 검산할 Evidence가 정의되었다.
실패 뒤의 Recovery Point가 있다.
```

완료상태 예:

```text
STRUCTURED_AND_READY_FOR_REVIEW
READY_FOR_EXECUTION
EXECUTED_AWAITING_VALIDATION
COMPLETE_AND_VERIFIED
PARTIAL_WITH_OPEN_ITEMS
HOLD_WITH_IDENTITY_FAILURE
HOLD_WITH_BOUNDARY_CONFLICT
```

# 15. Anti-Pattern

## 15.1 장문을 구조화로 오인

```text
많이 씀
≠
구조화 완료
```

같은 내용을 반복하더라도
Identity·Boundary·State·Validation이 없으면
실행 가능한 Program이 아니다.

## 15.2 AI가 빈칸을 임의 확정

```text
Source Missing
→ AI의 그럴듯한 추정
→ 즉시 실행
```

은 금지한다.

```text
Source Missing
→ OPEN 또는 HOLD
→ 근거 확보
→ 재결속
```

으로 진행한다.

## 15.3 코드 생성으로 완료 판정

```text
Code Generated
≠
Purpose Achieved
```

테스트·Readback·역검산이 없으면 완료가 아니다.

## 15.4 문서와 실행의 역할병합

설계문서가 직접 Mutation 권한을 자동 획득하지 않는다.

```text
Architecture
→ Directive
→ Approval
→ Execution
→ Validation
```

의 경계를 유지한다.

## 15.5 기존 객체 덮어쓰기

새 이론이나 Method는
기존 정본을 근거 없이 덮어쓰지 않는다.

```text
Previous Object
→ 보존

Difference
→ 새 객체

Relation
→ 명시
```

# 16. Repository 적용 제안

## 16.1 배치원칙

AI.Style은 공리 자체라기보다
공리를 사용하여 자연언어를 실행계약으로 만드는 Method다.

따라서 최초 배치 후보는 다음이다.

```text
SeungeFlow/Principle_C
└─ Start_Position
   └─ 06_methodology
      └─ <sha256>.C.md
```

기존 Method 문서를 수정하여 흡수하지 않고
새 독립 Method Object로 생성한다.

## 16.2 후속 참조 갱신 후보

검산과 승인 뒤 필요한 최소변경만 수행한다.

```text
06_methodology/CANDIDATE_METHOD_CATALOG.json
→ AI.Style Candidate 등록

README.md
→ 필요할 경우 선택적 진입링크 추가
```

다음 파일은 자동 수정하지 않는다.

```text
01_axioms/RELATION_GUARDS.md
04_structure/DIMENSIONAL_RECONSTRUCTION.md
05_process/DATA_FUNCTION_RESULT.md
```

AI.Style은 이들을 사용하고 Relation하지만
동일 본문을 복제하거나 병합하지 않는다.

## 16.3 Repository 반영 검산

```text
Repository
Branch
Before Commit
After Commit
Tree
Changed Files
New Files
File SHA-256
Catalog Binding
Duplicate Definition
Role Boundary
Push Status
Raw Readback
Web Readback
Fresh Clone Readback
```

# 18. 최종 정의

```text
AI.Style Programming은
사람이 자연언어로 목적·가치·Identity·경계·상태·관계를 정의하고,

AI가 그 언어를
모호성과 충돌을 숨기지 않는 구조계약으로 정규화하며,

필요한 Method를 선택하여
실행계획·코드·문서·데이터·도구행동으로 외부화하고,

결과를 원래 Purpose와 Source에
순방향·역방향으로 검산하는 프로그래밍 방식이다.
```

```text
글은 설명문에 머물지 않는다.

정확히 구조화된 글은
AI가 읽고 계획하고 구현하고 검산할 수 있는
상위 Program Source가 된다.
```

```text
Code is not removed.

Code becomes one executable Result
of a language-structured Program.
```
