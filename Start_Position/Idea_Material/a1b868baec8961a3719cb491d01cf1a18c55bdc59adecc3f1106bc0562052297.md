## 1. Track DB coordinate filename candidate

- Candidate naming pattern: `TrackDB_ZYX` using three decimal digits.
- Current examples: `TrackDB_000`, `TrackDB_001`, `TrackDB_123`.
- Proposed reading: `TrackDB_123` means `Z=1`, `Y=2`, `X=3`.
- Open questions:
  - Should the actual filename include semantic prefix plus coordinate, or should coordinate be metadata while final artifact filename remains SHA-256?
  - Is this an internal Track ID rather than the physical final filename?
  - How are more than 1000 Track DB objects represented: another coordinate cell, another directory boundary, additional digit width, or higher-level root?
  - Does the order remain `ZYX` in every rendering and database view?
- Important distinction: `000..999` are 1000 positions; `999` is the final address, not “one whole” in ordinary arithmetic counting.

## 2. Optical reflection projection

- Six cube faces, four local surface direction factors per face, and six center-normal directions.
- Candidate relation between 24 surface direction factors and six center factors.
- Reflection must be treated as an actual optical projection when used for light, not merely a generic return/error metaphor.
- Open question: exact minimal rendering grammar for incident ray, normal, reflected ray, transmitted ray, surface quadrant, and center relation.

## 9. Zero-domain notation candidate

- Candidate structural distinction:
  - first coordinate seat = position zero;
  - absent or uninstantiated state = state zero.
- Candidate transition vocabulary: an instance aligned at `0d(x)` becomes an active one-dimensional role-state `1d(x)` when the individual instruction assigned to that stage establishes its operational relation.
- Proposed symbolic annotations `0/1` and `0/0` are retained only as project-specific domain/occupancy markers, not as conventional arithmetic fractions.
- Validation questions:
  - Is `state zero` truly absence, or can it also be an explicit off-state carrying information?
  - Should undefined domain, empty domain, unoccupied seat, and off-state receive separate symbols?
  - Which denominator identifies the governing domain: position, state-space, instruction set, or instance existence?
  - How should the notation remain compatible with the earlier rule that binary `0/off` is itself a representable value?

## 10. Cell-layer and Plane-Body address candidate

- Candidate rendering rule: treat each orthogonal `Plane-Body (평면체)` as a Cell-occupied layer selected by the omitted-axis coordinate.
  - `XY@Z=k`
  - `XZ@Y=k`
  - `YZ@X=k`
- Fixed relation: one three-digit `ZYX` address identifies one Track DB Cell; `1 Cell = 1 Track DB`. Fixing one digit and varying the other two identifies one Plane-Body layer composed of multiple Track DB Cells.
- Example exploration:
  - fixed `Z=1`, variable `Y,X` → the `XY Plane-Body` containing `TrackDB_100..TrackDB_199` under a strict `ZYX` decimal-width convention;
  - fixed `Y=2`, variable `Z,X` → an `XZ Plane-Body` assembled from addresses whose middle digit is `2`;
  - fixed `X=3`, variable `Z,Y` → a `YZ Plane-Body` assembled from addresses whose final digit is `3`.
- Open validation questions:
  - Resolved: one Track DB is one Cell; remaining validation concerns how its event-state, document bytes, coordinate alias, and relation metadata are represented without splitting Cell identity.
  - Should a Plane-Body have its own manifest, or be reconstructed dynamically from Cell addresses?
  - Is the Plane-Body exactly one Cell thick on the omitted axis, or can thickness be a later rendering parameter while the seat remains fixed?
  - How are coordinate layers represented after any axis exceeds one decimal digit?
  - How should a hash-addressed immutable filename coexist with a mutable or relational coordinate alias?

## 12. Artificial return and Result.Data validation candidate

- Candidate process distinction:
  - autonomous processing path: `Data → Function → Result`;
  - user-mediated return path: `Result → Data seat`;
  - second-pass product: `Result.Data → Function → revised or next Result`.
- `A ⊕ B` is treated as the Function relation and `A′` as the Result-side target. The Function does not independently travel toward the prior Data seat.
- The term `artificial` identifies deliberate user intervention, not falsification: the user changes the position-role of an existing Result so it can be checked again.
- Candidate meaning of `│←`: reflection/re-entry used for review, verification, structural validation, correction, and supplementation.
- Candidate anti-misreading targets:
  - semantic misreading;
  - coordinate or viewpoint error;
  - visual illusion and perspective confusion;
  - mistaken assumptions;
  - judgment error;
  - omissions discovered only after a Result has been formed.
- Validation questions:
  - Which metadata proves that a `Result.Data` object came from a prior Result rather than raw source Data?
  - Should Track DB preserve separate coordinates for original Data, Result, and returned Result.Data?
  - How is the user-mediated seat change recorded without changing the immutable hash identity of the underlying Result bytes?
  - When does a correction create a new Result object, and when is it only a new relation pointer to the same object?
  - Can repeated return-validation cycles be represented as a Branch while keeping each pass independently verifiable?

## 14. Individual-instruction versus joint-instruction comparison material

- Fixed distinction:
  - joint instruction = a bundle containing multiple intended stage instructions;
  - individual instruction = one executable instruction placed in one stage seat;
  - one stage seat = one operational state value.
- A joint instruction can describe the whole workflow but cannot be treated as the direct control value for one instance stage when several targets, transitions, or expected Results are mixed inside it.
- Current operational comparison:
  - minimum candidate: five separate instructions for five structural stages;
  - preferred current workflow: eleven separate instructions for eleven stage seats;
  - comparison baseline: earlier GitHub Track DB Cells generated under prior mixed or bundled instruction structures;
  - comparison target: current Result.Data generated through stage-specific instruction entry.
- Comparison fields to preserve:
  - instruction count and stage mapping;
  - one-seat/one-state compliance;
  - source identity and input provenance;
  - omissions and mixed-state leakage;
  - error, illusion, assumption, and judgment-correction points;
  - Result-to-Result.Data return record;
  - final Result consistency across repeated validation.
- The earlier Track DB Cells are evidence, not failed objects to overwrite. Their contents are compared with current Result.Data to locate where instruction mixing changed the Result.
- Open validation questions:
  - Which five stages form the true minimum instruction set?
  - Are all eleven instructions always required, or can a stage be formally inactive while still retaining an explicit no-operation state?
  - How should a joint instruction package reference its eleven individual instructions without becoming a twelfth executable state?
  - What metric distinguishes a longer answer from a structurally better Result.Data?

## 15. Document-first versus bundled-input comparison material

- Comparison A — bundled input:
  - one combined document contains prior Data, explanations, examples, and several intended instructions;
  - the whole object is entered at once;
  - the instance must infer which parts are source Data, which parts are active instructions, and which instructions belong to later stages.
- Comparison B — prepared sequential input:
  - prior documents are uploaded first to the assigned `gpt.2d` or `gpt.3d` object;
  - the documents are read and operationally indexed as context preparation;
  - the current seat, source boundary, and expected end-position are established;
  - one individual stage instruction is then entered;
  - the Result is preserved before the next stage instruction is supplied.
- Current hypothesis:
  - when Data documents and several instructions are supplied without explicit object boundaries, both may be treated as competing input objects during interpretation;
  - staged entry may reduce source/instruction mixing, premature execution of later steps, omission, and target-boundary confusion;
  - this is a workflow hypothesis to validate through comparative Track DB evidence, not a universal claim about all model-internal embedding implementations.
- Required comparison targets:
  - earlier GitHub Track DB Cells produced from whole-document or bundled-instruction entry;
  - current Result.Data produced after document-first preparation and stage-specific instruction entry;
  - `gpt.2d` and `gpt.3d` objects under the same source document but different input sequencing.
- Proposed comparison fields:
  - source-document recognition;
  - active-instruction isolation;
  - end-position recognition before execution;
  - omission count;
  - source/instruction cross-contamination;
  - premature use of future-stage instructions;
  - provenance continuity;
  - correction and return-validation count;
  - consistency of Result.Data across repeated runs.
- Open validation questions:
  - What observable event proves that context preparation is complete?
  - Should readiness be recorded as a separate non-executable state before the first instruction?
  - Can one physical message safely carry Data and one instruction when their boundaries are explicit?
  - Does the benefit come from temporal separation, semantic labeling, smaller context scope, or all three?
  - How should the eleven-stage workflow record the source document once without redundantly re-uploading it at every stage?
  - Which earlier Track DB Cells provide the cleanest whole-input baseline for comparison?
