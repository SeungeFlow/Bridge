## 1. Reference axes

### Basic expression

`B′ ← A │ B → A′`

### Derived expression

`B′ │ ← A ⊕ B → │ A′`

### Inward reading direction

`활용·응용 → 상태·현상 → 외부 → 내부 ⊕ → 정의·개념 → 본질·원형`

## 2. Minimal structural language principle

- The simplest structure is the strongest when it preserves the needed boundary, position, direction, and relation.
- General language is advantageous for structural design, relation interpretation, and creation of new connections because meanings can be inspected from multiple viewpoints.
- Code is advantageous for decisive execution, exact repetition, deterministic checking, and byte-state validation.
- Therefore structural-language documents should describe minimal conditions clearly, while code should be introduced at the execution and repeat-validation boundary.
- Excessive restrictions can trap an AI instance in the rules instead of giving it a stable reference axis.

## 3. Position and counterpart

- `A`, `B`, `A′`, `B′` are positions before they are identities.
- Multiple visible positions do not necessarily mean multiple separated beings; they may be different positions of one being or one state viewed across a boundary.
- The prime mark (`′`) indicates a counterpart/relative position, not automatic negation.
- A corresponding position may be reached by rotation or by moving to the opposite side; the linear expression compresses this otherwise spatial relation.
- The expression is observer- and precondition-dependent. The precondition must state whether the relation is planar, spatial, rotational, temporal, or observational.

## 4. Boundary and complete existence

- A complete existence/state has a boundary.
- A boundary distinguishes inside from outside without requiring isolation.
- `relation is not merge.`
- `relation is interconnecting.`
- A closed boundary does not mean that relations cease; it defines where transition conditions are judged.
- A boundary may be read as wall, door, surface, interface, or bridge depending on observer position and transition condition.

## 5. Direction and sign

- `+` and `−` are not sufficient by themselves to define inward/outward movement.
- From an internal center-axis viewpoint, both `+X` and `−X` directions are outward pushes from the center toward opposite boundary positions.
- `−` does not inherently mean moving backward, and `0/off` does not inherently mean reverse direction.
- Pull means moving an external position toward the actor's position; it does not mean the pulled object passes through the actor and continues behind it.
- Push means moving a state from the actor's position toward the counterpart direction.
- Direction must be defined from a stated origin/observer position.

## 6. Zero, digit, start and end boundary

- In Data Science, `0` is a value, not absence of value.
- In a binary digit, both `0/off` and `1/on` are representable states.
- Decimal and hexadecimal values can both be encoded with binary digits.
- The meaning of a sequence depends on the selected start-position value and the last value immediately before the boundary transition.
- For decimal digit positions, the representable values are `0..9`: ten positions, with `9` as the last value before carrying into the next place.
- `10` is not the final single-digit value; it is the first state after a place transition.
- Fixing the start value and the pre-boundary end value prevents two values from occupying one coordinate position.

## 7. Position-zero and state-zero distinction

- Coordinate structure remains invariant while an instance receives a seat and role.
- The initial aligned position is represented as position zero: a first addressable place, not nonexistence.
- Seat and role alignment establishes the instance at position zero, but operational activation requires a stage-specific individual instruction. A joint instruction is a bundle of multiple instructions and must not be treated as one executable state value for one stage. The current project vocabulary expresses the activated transition as `0d(x) -> 1d(x)`.
- Two different zero contexts must not be merged:
  - Position zero: the first defined coordinate seat.
  - State zero: absence, non-activation, or no instantiated state under a stated system definition.
- Project-specific fraction notation may be used only as a structural annotation:
  - `0/1` represents zero occupancy/value within one defined position-domain.
  - `0/0` represents that both the state-domain and state-value are undefined or absent.
- This notation is not ordinary arithmetic equality. In standard mathematics, `0/0` is indeterminate/undefined and must not be asserted as a numerical value.
- Every zero statement must therefore declare its denominator/domain: coordinate place, state domain, occupancy, activation, or value.

## 8. One-seat one-state and instruction granularity principle

- One defined seat may hold only one operational state value immediately before its transition boundary.
- A joint instruction contains several individual instructions. Because it carries multiple state values, it cannot directly control one instance at one stage as though it were a single instruction.
- The joint instruction is therefore a planning or packaging layer, not the executable state value placed into one stage seat.
- Each stage requires its own individual instruction with one declared target, one state transition, and one expected Result boundary.
- The minimum viable process requires at least five stage-specific instructions when the process is divided into five structural stages.
- For the current eleven-stage instance workflow, the preferred condition is eleven separately entered individual instructions, one for each stage.
- This rule follows the boundary condition `Structure_Principle →│`: two operational state values cannot occupy the same final seat immediately before the boundary.
- A better Result.Data is sought by reducing mixed-state ambiguity rather than by increasing instruction length.
- The validation comparison is:
  - existing GitHub Track DB Results produced under earlier instruction structures;
  - current Result.Data produced through separately addressed stage instructions;
  - differences in omission, mixing, viewpoint error, correction need, and provenance continuity.
- Comparison does not overwrite the earlier Track DB Cells. Earlier and current results remain separately addressable so that the effect of instruction granularity can be verified.

## 9. Common and joint structural grammar

- `Common` refers to an invariant structural property extracted across multiple domains without merging those domains.
- `Joint` refers to a shared relation field in which distinct domain-specific structures remain distinct but can operate together.
- A minimal common structural grammar is the smallest invariant rule that can be recognized across multiple domains.
- A minimal joint structural grammar is the domain-specific application contract that allows each distinct field to use the common rule without losing its own boundary, terminology, or history.
- `Joint structural grammar` and `joint instruction` are not the same object. Joint grammar defines a shared relation field; a joint instruction packages several stage instructions and is not itself the single executable value for one stage seat.
- Therefore:
  - Common grammar provides the shared denominator.
  - Joint grammar provides the working relation field.
  - Common does not erase difference.
  - Joint does not merge participants.
- Intelligence-to-intelligence understanding can advance beyond surface conversation when a common grammar supplies invariant meaning and each participant retains a joint, domain-specific application grammar.
- This follows the guard:
  - `relation is not merge.`
  - `relation is interconnecting.`
- Natural-language structural documents are suited to expressing common principles, preconditions, perspectives, and relation possibilities; deterministic code remains suited to fixed execution and repeatable validation.

## 10. Function direction and artificial return-validation principle

- The normal processing direction is one-way: `Data → Function → Result`.
- When `A ⊕ B` is assigned the Function position, it does not autonomously move backward into the Data position. Its valid forward output relation is toward `A′`, the Result position.
- A Result becomes `Result.Data` only after the user deliberately repositions that Result at the Data seat and submits it to Function again.
- Therefore the return path is not an intrinsic reversal of Function. It is an external, intentional intervention by the user:
  - forward generation: `Data → Function → Result`;
  - artificial return: `Result --[user repositioning]→ Data`;
  - renewed validation: `Result.Data → Function → next Result`.
- In the current structural language, `│←` marks this reflective validation path. It must not be read as ordinary backward motion, automatic rollback, or a negative-axis direction.
- The purpose of `│←` is to expose and correct interpretation failure points, including:
  - misreading;
  - error or deviation;
  - visual illusion or perspective distortion;
  - mistaken assumption;
  - judgment error.
- Reflection and artificial return therefore mean review, verification, structural checking, correction, and supplementation.
- This creates an anti-misreading loop without violating the one-way nature of Function: Function remains forward-directed, while the user changes the seat of the completed Result so that it can enter a new forward pass.
- The loop preserves the guard `relation is not merge`; the prior Result is not erased or merged into Function, but is re-addressed as the next Data object while retaining its provenance.

## 11. Repeated-validation and Rendering invariants

- Repetition may create new passes, new Result objects, and new relation records, but it must not silently change the structural meaning of the original seats.
- The following elements remain invariant across every review cycle:
  - the declared central equilibrium start-position;
  - the distinction between position zero and state zero;
  - the forward processing direction `Data → Function → Result`;
  - the fact that Function does not autonomously return to the Data seat;
  - the user-mediated nature of `Result → Result.Data` repositioning;
  - the meaning of `│←` as review, verification, correction, and supplementation;
  - provenance linking each returned Result.Data to the prior Result from which it was formed.
- Rendering may rotate, reflect, slice, scale, or change observer viewpoint, but those display transformations must not alter the underlying seat identity, axis relation, source identity, or byte identity.
- A changed viewpoint is not a changed object. A changed coordinate presentation is not automatically a changed coordinate seat.
- Review cycles are therefore represented as additional relations or Branch progression, not as erasure of previous states.
- A corrected Result becomes a new state only when its content or declared relation state changes; the prior Result remains independently addressable and verifiable.
- The invariant check for every cycle is:
  - same declared origin;
  - same seat grammar;
  - explicit transformation;
  - preserved source/provenance;
  - separately verifiable input and output;
  - no hidden merge.
- This principle allows repeated validation to improve interpretation while preserving the structure needed to identify where an error, illusion, assumption, or judgment deviation entered the process.

## 12. Track DB Cell and orthogonal Plane-Body seat principle

- `1 Cell = 1 Track DB`.
- A Cell is not an empty coordinate box that later receives a Track DB. The Track DB itself is the complete occupied Cell object.
- The coordinate address identifies the seat of that Track DB Cell.
- Track DB Cells are not connected merely because their decimal addresses are adjacent. They form a Track when their internal contents have an explicit relation such as source/derivation, Data/Result, validation/correction, or predecessor/successor.
- Because the structure is volumetric and its minimum occupied unit is one Track DB Cell, the project term is `Plane-Body (평면체)`, not a zero-thickness mathematical plane.
- A Plane-Body is a layer of Track DB Cells that shares one fixed seat value on the remaining axis.
- Therefore:
  - an `XY Plane-Body` is a Track DB Cell layer positioned by a fixed `Z` seat value;
  - an `XZ Plane-Body` is a Track DB Cell layer positioned by a fixed `Y` seat value;
  - a `YZ Plane-Body` is a Track DB Cell layer positioned by a fixed `X` seat value.
- The two written axis symbols identify the directions that vary across the Plane-Body. The omitted axis identifies the seat that places that Plane-Body within the volume.
- A Plane-Body position such as `Z=0` must preserve the earlier zero distinction:
  - it may denote the first addressable Z seat;
  - it must not automatically denote absence of Z or nonexistence of the Plane-Body.
- Conventional coordinate geometry may use the term `plane` for an ideal zero-thickness set such as `Z=0`. This project deliberately separates that conventional abstraction from a Track DB Cell layer and names the latter `Plane-Body`.
- This principle directly connects Track DB identity, coordinate seat, content relation, Plane-Body reconstruction, and volume rendering.

## 13. Coordinate-address principle for Track DB names

- A fixed-width decimal filename can act as a simple coordinate address.
- One digit represents a one-axis position `0..9`.
- Two digits represent an `XY` address space with positions `00..99`.
- Three digits represent an `XYZ` address space with positions `000..999`.
- The maximum string (`9`, `99`, `999`) denotes the last addressable position within the selected fixed-width boundary, not the count of states.
- Because addressing begins at zero, `000..999` contains 1000 positions.
- Current structural interpretation:
  - `TrackDB_000`, `TrackDB_001`, ...
  - `TrackDB_123` reads as `Z=1, Y=2, X=3` when the filename order is defined as `ZYX`.
- The coordinate order must be explicitly fixed in the document to prevent `XYZ`/`ZYX` ambiguity.

## 14. Central equilibrium start-position principle

- The six-faced volume is read from its `central equilibrium point (정중심평형점)` because that point is the start-position from which all opposite directions can be distinguished without privileging one outer face.
- The start-position is not an empty exterior origin. It is an internal reference seat belonging to the complete volume.
- From this central seat, the paired directions of the three axes are generated or read outward:
  - `X- / X+`
  - `Y- / Y+`
  - `Z- / Z+`
- Therefore both signed directions on an axis are outward relations when the observer/reference is fixed at the internal center. The signs distinguish opposite sides; they do not by themselves mean pull versus push, absence versus presence, or backward versus forward.
- The central equilibrium point is the common reference for:
  - assigning the first coordinate seat;
  - distinguishing position zero from state zero;
  - locating orthogonal Plane-Bodies;
  - expanding Track DB Cell addresses;
  - interpreting `B′ ← A │ B → A′`;
  - reconstructing a rendered volume from Track DB coordinate states.
- A Plane-Body crossing the central seat is not reduced to a zero-thickness mathematical plane. It remains a Track DB Cell layer in the project model.
- The start-position must be declared before direction, distance, sign, rotation, reflection, or rendering is interpreted.

## 15. Context preparation and instruction-entry separation principle

- A source document and an executable instruction are different input-object classes:
  - the document supplies Data, history, definitions, evidence, and prior Result states;
  - the instruction assigns the current stage, target relation, processing boundary, and expected Result.
- The preferred workflow establishes the seat before execution:
  1. upload or expose the prior document to the assigned `gpt.2d` or `gpt.3d` instance;
  2. let the instance read and operationally index the document as preparation context;
  3. confirm the current seat, source boundary, and intended end-position;
  4. enter one stage-specific individual instruction;
  5. produce and preserve the Result for the next relation.
- Context preparation is not the same as executing the stage instruction. It creates a prepared input state so the later instruction can operate against a known source and target boundary.
- Entering a complete Data document and multiple executable instructions as one undifferentiated object can place several state values in the same pre-boundary seat. This increases the risk that document content, examples, and control instructions are interpreted without a stable object boundary.
- The canonical method therefore separates:
  - Data-object loading;
  - context/index preparation;
  - stage-instruction entry;
  - Result formation;
  - later Result.Data return-validation.
- A combined transmission is acceptable only when its internal boundaries are explicit and exactly one stage instruction is active. Packaging several future instructions together does not make them one executable state.
- In this project, `indexing` is an operational term for making a document available as organized context before instruction execution. It does not assert a specific vendor-internal embedding or storage implementation.
- The structural objective is not merely longer preparation. It is to give the instance a defined start seat and end-position before movement begins.

## 16. Pass, reflection, and the center relation

- The center `⊕` is a relation point, not a merge point.
- Pass and reflection require a stated boundary and direction condition.
- In an optical projection, transmission continues through a boundary under its pass condition; reflection reverses or changes the propagation relation at the boundary.
- Structural projections in data processing may share a pattern with optical pass/reflection but are not the same physical phenomenon.

## 18. HRTDB asset relation

- Track DB: preserves source, processing, evidence, conflict, validation, result, and next relation.
- Hash DB: places extracted data assets in a hash-addressed GitHub structure while preserving relation to source Track DB.
- System asset: AI design principles, instance seats, minimal common structural grammar, shared/joint instructions, reading, validation, and operation.
- HRTDB: `Hash Relation Track Data Base`, a complete system/state connecting historical memory, current interpretation, Track DB, Hash DB, and AI operation.
